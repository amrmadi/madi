# ElderLife AI — Power BI Guide

> **No `.pbix` file exists in this repository, and none may be claimed to exist.**
> A Power BI report is an artefact of the Power BI **desktop application**: the
> file format is produced by that application and cannot be generated by a
> script, a CI job, or a commit. Until somebody opens Power BI Desktop, builds
> the report by hand and saves it, the deliverable of this project is the **CSV
> export** described below — not a report.
>
> This is stated at the top of the document on purpose, because "the Power BI
> report is done" is the easiest false claim in this project to make by
> accident.

This document exists to make the reporting step reproducible by someone who has
never seen it: how to get the data out of PostgreSQL, how to load it into Power
BI Desktop, what to build, and — most importantly — **what the report must not
say**.

---

## 1. What the export produces

The analytics layer in `analytics/` is a set of **read-only SQL views** over the
operational tables, plus an export script that turns them into flat files.

| Output | What it is |
|---|---|
| **One CSV per analytics view** | A flat file named after the view, with one row per grain row |
| **`_manifest.json`** | Provenance for the export: what was exported, when, from which database (password redacted), how many rows, and which columns |

The 8 views the export produces, with their grain and the honesty columns they
carry. The names and columns below are taken from the SQL files themselves in
[`analytics/sql/`](../analytics/sql/), which is the authority:

| View | SQL file | Grain | Honesty columns it carries |
|---|---|---|---|
| `v_alert_lifecycle_daily` | `01_alert_lifecycle_daily.sql` | resident × day | `open_alert_count` vs `resolved_alert_count` + `dismissed_alert_count`; `distinct_caregiver_count` counts only caregivers who actually acknowledged something |
| `v_alert_acknowledgement_performance` | `02_alert_acknowledgement_performance.sql` | alert | `is_acknowledged`; `seconds_to_acknowledge` is **NULL** for alerts nobody acknowledged; `occurrence_count` = how often the same problem was re-detected |
| `v_alert_priority_backlog` | `03_alert_priority_backlog.sql` | resident × severity × alert type (open alerts only) | `oldest_open_alert_created_at` — the age of the *oldest* open alert in the group, not an average |
| `v_checkin_completion_daily` | `04_checkin_completion_daily.sql` | resident × day | `excluded_pending` (scheduled + cancelled) — **not** failures; `resolved_checkins` = taken + missed + skipped |
| `v_medication_adherence_daily` | `05_medication_adherence_daily.sql` | resident × medication schedule × day | `resolved_doses` vs `taken_doses` — **logged doses only**; an unlogged dose cannot be counted |
| `v_care_plan_adherence` | `06_care_plan_adherence.sql` | resident × care plan × plan item | `has_positive_outcome`; `taken_dose_count`, `taken_checkin_count` for context. `note` and `reminder` items are **not in the view at all**, because they cannot produce a measurable outcome |
| `v_model_run_metrics` | `07_model_run_metrics.sql` | model run | `has_metrics` (coverage, **not** quality); `has_failed`; `duration_seconds` is **NULL** while a run has not finished |
| `v_resident_activity_summary` | `08_resident_activity_summary.sql` | resident × day | `simulated_event_count`, `imported_dataset_event_count`, `non_simulated_event_count`, `all_events_simulated`; `verified_fall_event_count` vs `fall_event_count` |

> **A discrepancy in the existing docs, stated rather than hidden.**
> [`erd.md`](erd.md#reporting-layer-views-not-tables) lists the reporting layer
> under different names — `analytics_checkin_daily`, `analytics_alerts_daily`,
> `analytics_caregiver_acknowledgement`, `analytics_care_plan_adherence`,
> `analytics_activity_daily`, `analytics_model_runs`,
> `analytics_resident_rollup`, `analytics_kpi_definitions`. **Those view names
> do not exist.** The views that actually exist are the `v_*` names above, and
> their columns differ from the ERD's list as well. This guide uses the real
> names, because the real names are the ones a Power BI import will show.
> `erd.md` is an existing file and has not been edited; reconciling it is
> open work (see [roadmap.md](roadmap.md#9-current-state)).

The manifest is what makes the export auditable: a report built from a CSV set
can say *when* it was produced, *from what*, and *over which window* — which is
the difference between a report and a rumour.

### A second, smaller source of truth: the KPI endpoint

The API already exposes the KPI catalogue as CSV, so a report can be built
without touching the database directly:

```
GET /api/v1/analytics/kpis.csv?start=<ISO-8601>&end=<ISO-8601>
```

- **Access: `admin` or `analyst` only** — caregivers get `403`, because
  cross-resident aggregates are not raw care records.
- `start` and `end` are **required**. A KPI without its window is meaningless,
  so the window is not an optional filter with a hidden default.
- The CSV carries `kpi_key`, `kpi_name`, `unit`, `value`, `numerator`,
  `denominator`, `window_start`, `window_end`, `excluded_missing`,
  `is_measurable`, `unmeasurable_reason`, `missing_data_note`.
- The 8 `kpi_key` values are: `alert_acknowledgement_rate`,
  `alert_median_ack_seconds`, `alert_resolution_rate`,
  `high_priority_alert_count`, `checkin_completion_rate`,
  `medication_adherence_rate`, `care_plan_adherence_rate`,
  `model_metric_coverage`.

That last column set is what the honesty rules in §6 are built on.

## 2. Producing the export

> **Current state.** `analytics/export_analytics.py` and the eight files in
> `analytics/sql/` **do exist** in the working tree, and the commands below
> are the real ones, taken from the script itself. What does **not** exist yet
> is the output: `analytics/exports/` is **not present** in the working tree, so
> there is no CSV set and no `_manifest.json` here. Task **T5** in
> [CONTRIBUTING.md](../CONTRIBUTING.md#open-tasks) is therefore still open.

### Step 1 — apply the SQL views to PostgreSQL

The views must exist in the database before anything can be exported from them.
The database is the `db` service in the Compose stack.

```powershell
# The stack must be up and healthy first:
docker compose up -d db
docker compose exec backend alembic upgrade head      # the tables the views read

# Apply every view file, with ON_ERROR_STOP=1 so the first error aborts.
# The files live on the host, so they are piped into psql inside the container:
Get-ChildItem analytics\sql\*.sql | ForEach-Object {
  Get-Content $_.FullName -Raw |
    docker compose exec -T db psql -U elderlife_dev -d elderlife -v ON_ERROR_STOP=1
}

# Confirm the views exist and return rows:
docker compose exec -T db psql -U elderlife_dev -d elderlife -c "\dv v_*"
docker compose exec -T db psql -U elderlife_dev -d elderlife -c "SELECT count(*) FROM v_alert_lifecycle_daily;"
```

| Detail | Value |
|---|---|
| Host | `localhost` (the container publishes `5432`) |
| Port | `5432` (change with `DB_PORT` in `.env`) |
| Database | `elderlife` |
| User / password | `elderlife_dev` / the value of `POSTGRES_PASSWORD` in your local `.env` — **never commit it** |
| `ON_ERROR_STOP=1` | **Required.** Without it `psql` keeps going after an error and you get half-created views and a clean exit code. That failure mode is exactly what a "verified" claim must not hide. |

Before you apply anything, the SQL can be checked offline against the models,
with no database and no dataset:

```powershell
.\.venv\Scripts\python.exe tools\validate_analytics_sql.py
```

It resolves every table and column named in `analytics/sql/` against the
SQLAlchemy models and prints how many references it could and could not check.

### Step 2 — run the export

```powershell
# Export every view:
.\.venv\Scripts\python.exe analytics\export_analytics.py

# Create the views first (from analytics/sql/), then export:
.\.venv\Scripts\python.exe analytics\export_analytics.py --apply-sql

# Export a subset:
.\.venv\Scripts\python.exe analytics\export_analytics.py --views v_alert_lifecycle_daily,v_model_run_metrics

# Write the CSVs somewhere else:
.\.venv\Scripts\python.exe analytics\export_analytics.py --output-dir D:\reports\elderlife

# Point at a specific database:
.\.venv\Scripts\python.exe analytics\export_analytics.py --database-url "postgresql://user:pass@localhost:5432/elderlife"
```

| Question | Answer |
|---|---|
| Where do the CSVs go? | `analytics/exports/` by default — **git-ignored** (`analytics/exports/**`), so a report is never committed by accident |
| What else is written? | `_manifest.json` in the same folder, recording provenance |
| Which database? | `--database-url`, else the `DATABASE_URL` environment variable, else the placeholder in `.env.example`. The `postgresql+psycopg://` scheme is normalised to `postgresql://` for the driver |
| Does it need the dataset or the trained model? | **No.** The export is purely operational data. This is what makes task **T5** independent of tasks T1/T2 |
| What does it need installed? | `psycopg` — `pip install "psycopg[binary]"`. It is imported lazily, so `--help` works without it, but the export does not |
| What if a view is missing? | The script **exits non-zero and writes nothing**. It never writes an empty CSV, because an empty CSV is indistinguishable from "there was no activity" |

### Step 3 — (alternative) pull the KPI CSV from the API

```powershell
# Requires an admin or analyst token:
curl -H "Authorization: Bearer <token>" `
  "http://localhost:8000/api/v1/analytics/kpis.csv?start=2026-10-01T00:00:00Z&end=2026-10-21T00:00:00Z" `
  -o analytics\exports\elderlife_kpis_20261001_20261021.csv
```

## 3. Loading the CSVs in Power BI Desktop

Power BI Desktop (Windows, free) is required for this step — there is no
headless equivalent, which is the reason this guide cannot ship a `.pbix`.

1. **Get Data → Text/CSV** (or *Get Data → More → File → Text/CSV* for the
   multi-file case).
2. Point it at `analytics\exports\*.csv`. For several files at once, choose the
   **folder** and use *Combine & Transform*.
3. In the CSV import screen, set the **File Origin** to *Windows File System*,
   and check **"Detect column type"** so ISO-8601 timestamps become date/time
   values rather than text.
4. Choose the right types by hand where the automatic detection is wrong:
   - `alert_day`, `checkin_day`, `dose_day`, `event_day` → **Date**
   - `created_at`, `acknowledged_at`, `resolved_at`, `started_at`,
     `finished_at`, `oldest_open_alert_created_at`,
     `newest_open_alert_created_at`, `earliest_acknowledged_at` → **Date/Time**
   - `seconds_to_acknowledge`, `seconds_to_resolve`, `duration_seconds` →
     **Decimal Number**
   - `average_anomaly_score`, `average_risk_score` → **Decimal Number**
   - `is_acknowledged`, `has_metrics`, `has_failed`, `has_positive_outcome`,
     `item_is_active`, `all_events_simulated` → **True/False** — do not leave
     these as text, the honesty rules depend on them
   - `*_count`, `*_alerts`, `*_doses`, `*_checkins` → **Whole Number**
   - `metrics_json` → **Text**. It is raw JSON, and it is left as text on
     purpose, so nothing is flattened into a number that was never measured
5. Load each view as its own table. **Rename them to the view name** — the
   table name is what appears in the report's field list, and `Table1`/`Table2`
   make a report unreadable.

## 4. The import model

Keep it simple. A star schema is enough for this data and is far easier to
audit than anything cleverer.

| Step | What to do |
|---|---|
| **Date table** | `Home → Enter date table` with a start and end date covering the data, then mark it as the date table. Without one, time-intelligence functions (year-to-date, moving averages) silently return odd results. |
| **Resident dimension** | One row per resident, built from `elderly_profile_id` + `elderly_profile_display_name` (present in every `v_*` view that is keyed by resident). Relate the daily views to it on `elderly_profile_id`. |
| **Caregiver dimension** | One row per caregiver, from `acknowledged_by_user_id` + `acknowledged_by_display_name` in `v_alert_acknowledgement_performance`. Rows for alerts nobody acknowledged have a NULL id — that NULL is the honest answer, not a value to fill in. |
| **Fact tables** | `v_alert_lifecycle_daily`, `v_checkin_completion_daily`, `v_medication_adherence_daily`, `v_resident_activity_summary` (per resident × day); `v_alert_acknowledgement_performance` and `v_model_run_metrics` (per row); `v_care_plan_adherence` (per plan item); `v_alert_priority_backlog` (a current-state snapshot, not a time series). |
| **KPI table** | The KPI CSV from §1 (or `GET /api/v1/analytics/kpi-definitions`) as a **standalone** table, **not** joined — it is a definition/value catalogue, not a fact. |
| **Relationships** | One-to-many, dimension on the "one" side, single direction, with the filter flowing from dimension to fact. |
| **Do not** | Build relationships between views on columns that are not keys. Cross-join fan-out is how a report starts showing numbers that do not match the API. |

### Measure suggestions (DAX)

Use these as starting points; they mirror the KPI definitions in
[`alert-rules-and-kpis.md`](alert-rules-and-kpis.md) exactly.

```DAX
-- Alert acknowledgement rate: numerator / denominator, with the excluded count
-- always shown next to it. Never a bare ratio.
Alert Acknowledgement Rate =
DIVIDE(
    [Alerts Acknowledged],
    [Alerts Created]
)

-- The count that must accompany every rate above.
Alerts Not Acknowledged =
COUNTROWS( FILTER( 'v_alert_acknowledgement_performance', NOT 'v_alert_acknowledgement_performance'[is_acknowledged] ) )

-- Median time to acknowledge, in seconds. Median, not mean: one very late
-- acknowledgement should not distort the picture. Rows that were never
-- acknowledged have a NULL seconds_to_acknowledge and drop out of the median
-- by construction — so the not-acknowledged count above must be shown too.
Median Ack Seconds =
MEDIANX(
    'v_alert_acknowledgement_performance',
    'v_alert_acknowledgement_performance'[seconds_to_acknowledge]
)

-- Open (not finished) alerts. Open is not "failed" — it is work not yet closed.
Open Alerts =
SUM( 'v_alert_lifecycle_daily'[open_alert_count] )

-- Check-in completion. The pending/excluded count is part of this measure's
-- story and must be displayed with it.
Check-in Completion Rate =
DIVIDE(
    [Check-ins Taken],
    'v_checkin_completion_daily'[resolved_checkins]
)

-- Medication adherence among LOGGED doses only. This cannot see a dose that
-- was never logged, and the visual must say so.
Medication Adherence Rate =
DIVIDE(
    [Doses Taken],
    'v_medication_adherence_daily'[resolved_doses]
)

-- Model-run metric coverage: whether metrics EXIST, not whether they are good.
Model Metric Coverage =
DIVIDE(
    [Finished Runs With Metrics],
    [Finished Runs]
)

-- The simulated-data flag, used to label panels rather than to filter them away.
Any Simulated Activity =
CALCULATE(
    COUNTROWS( 'v_resident_activity_summary' ),
    'v_resident_activity_summary'[all_events_simulated] = TRUE()
)
```

> Every one of these must be paired with the **excluded / missing count** for
> the same window. A rate on its own is how a report starts lying — see §6.

## 5. What to build

Five pages. Each one answers one operational question, and each one carries its
own date window and honesty note.

### Page 1 — Care workload

*Question: how much attention did the residents need this period?*

| Visual | Built from | Notes |
|---|---|---|
| Alerts by day and severity | `v_alert_lifecycle_daily` | Severity is **operational triage priority**, not medical risk — say so on the page |
| Open / unacknowledged alerts | `v_alert_lifecycle_daily`, `v_alert_priority_backlog` | Show `open_alert_count` and `oldest_open_alert_created_at` explicitly |
| Residents with the most alerts | `v_alert_lifecycle_daily` | One row per resident from the dimension |
| Acknowledgement latency by caregiver | `v_alert_acknowledgement_performance` | Median, with the not-acknowledged count beside it |

### Page 2 — Alert performance

*Question: how quickly and how reliably are alerts handled?*

| Visual | Built from | Notes |
|---|---|---|
| Acknowledgement rate over time | `v_alert_lifecycle_daily` | Beside `open_alert_count` |
| Median time to acknowledge | `v_alert_acknowledgement_performance` | Include the not-acknowledged count |
| Alerts raised vs. deduplicated | `v_alert_lifecycle_daily` + `occurrence_count` | `occurrence_count` shows the deduplication working |
| Resolution rate | `v_alert_lifecycle_daily` | Open alerts are not failures — they may simply not have had time yet |

### Page 3 — Medication adherence

*Question: how much of the medication plan was recorded as taken?*

| Visual | Built from | Notes |
|---|---|---|
| Adherence rate per resident | `v_medication_adherence_daily` | With `resolved_doses` beside it |
| Doses taken / missed / skipped | `v_medication_adherence_daily` | The denominator is **logged** doses only |
| Care-plan item outcomes | `v_care_plan_adherence` | `has_positive_outcome`, with `taken_dose_count` / `taken_checkin_count` for context. There is no date window here — "at least once, ever" — so use the API KPI for time-boxed reporting |

### Page 4 — Check-in completion

*Question: are the scheduled wellbeing check-ins actually happening?*

| Visual | Built from | Notes |
|---|---|---|
| Completion rate per day | `v_checkin_completion_daily` | Beside `excluded_pending` |
| Pending vs. taken vs. missed | `v_checkin_completion_daily` | Pending check-ins are **not yet failures** |
| Unresolved check-ins | `v_checkin_completion_daily` | `total_checkins` − `resolved_checkins` |

### Page 5 — Model-run coverage

*Question: how much of the AI work actually ran, and how much of it recorded
metrics?*

| Visual | Built from | Notes |
|---|---|---|
| Runs by status | `v_model_run_metrics` | `pending`/`running` rows have a NULL `duration_seconds` — that is the truth, not a zero |
| Metric coverage | `v_model_run_metrics` | `has_metrics` — this measures whether metrics **exist**, never whether they are good |
| Runs with errors | `v_model_run_metrics` | `has_failed` and `error_message` — a failed run is a legitimate, useful record |
| Verified vs. total fall events | `v_resident_activity_summary` | `verified_fall_event_count` vs `fall_event_count` — never present the total as if it were confirmed |
| Demo vs. real readings | `v_resident_activity_summary` | `simulated_event_count` and `all_events_simulated` |

## 6. The honesty rules this report must respect

These are not stylistic preferences. They come from
[CONTRIBUTING.md → Project rules](../CONTRIBUTING.md#project-rules-you-must-follow)
and from the KPI definitions themselves.

1. **Label demo and simulated data as such.** A report built on seeded demo
   rows must say so on every page. The views carry the columns for this:
   `simulated_event_count`, `imported_dataset_event_count` and
   `all_events_simulated` in `v_resident_activity_summary`. Do not hide them
   in a tooltip — put the label where the number is.
2. **Never present a KPI as a medical outcome.** These KPIs measure the **care
   workflow**, not the residents' health. `high_priority_alert_count` is a
   triage-priority count, not a medical-risk count. `medication_adherence_rate`
   measures what was *recorded*, not what was taken.
3. **Always show the date window and the excluded-missing count next to any
   rate.** A rate without its window has no meaning, and a rate without its
   excluded count hides the very rows that make it low. In the KPI CSV these
   are `window_start`, `window_end` and `excluded_missing`; in the views the
   equivalents are `excluded_pending` (check-ins), `resolved_checkins`,
   `resolved_doses` and the `is_acknowledged` / `seconds_to_acknowledge` pair.
4. **A KPI with no value is "not measurable", not zero.** When
   `is_measurable` is `false`, show the `unmeasurable_reason`. A `0 %`
   acknowledgement rate on an empty window reads as "the team failed"; the
   truth is "there was nothing to acknowledge".
5. **Never invent a metric.** If a number is not in the export, it is not in
   the report. Model quality metrics (precision, recall, F1) come from the
   model evaluation pipeline — they are not KPI values, must not be
   reverse-engineered from the coverage ratio, and are not present in
   `v_model_run_metrics` beyond the raw `metrics_json` text.
6. **Distinguish a detection prompt from a confirmed event.**
   `v_resident_activity_summary` separates `verified_fall_event_count` from
   `fall_event_count` for exactly this reason. A fall-detection prediction is a
   prompt for a human to check; it is not a fall that happened.
7. **Show the provenance.** Put the export's date window and the
   `_manifest.json` details on the report (for example in a footer or a
   subtitle). A report that cannot say when it was produced cannot be
   reproduced.
8. **No personal data in the report.** Aggregates only. The API enforces this
   too: analytics endpoints are `admin`/`analyst`, and caregivers get `403`.

## 7. What is not done yet

- **No `.pbix` file exists in this repository**, and none may be claimed to
  exist. Building one requires Power BI Desktop, and no part of the build can
  be automated from this repository.
- **No export output is present.** `analytics/export_analytics.py` and the eight
  SQL files exist, but `analytics/exports/` does not exist in the working tree,
  so there is no CSV set and no `_manifest.json` here yet.
- **The analytics views have only been run over demo data.** All 8 views were
  created and queried against a real PostgreSQL container, but never at a scale
  where query plans or indexes matter.
- **The KPI API has been exercised; a Power BI file has never been opened
  against any export.** No report, no screenshot, no page — all of that is
  still to do, and it is task **T5** in
  [CONTRIBUTING.md](../CONTRIBUTING.md#open-tasks).
- **`docs/erd.md` still lists the old `analytics_*` view names**, which do not
  exist. Reconciling the ERD with `analytics/sql/` is open work; this guide
  uses the real names and says so in §1.
